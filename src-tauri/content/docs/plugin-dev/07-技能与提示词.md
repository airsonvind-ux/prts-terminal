# 07 技能与提示词

技能是一段**给模型的说明**：什么时候该用你的工具、参数怎么填、结果怎么读。
它不是代码，是提示词，模型在需要时自己决定激活。

## 放在哪

```text
my-plugin/
├─ plugin.json
└─ skills/
   └─ 查干员/
      └─ SKILL.md
```

目录名就是技能名。`plugin.json` 里声明一下：

```json
"contributes": { "skills": ["查干员"] }
```

声明与目录不一致时**以目录为准**，宿主只打一条提示——写了声明却没这个目录，
不算错误，但会少一个技能。

## SKILL.md

```markdown
---
name: 查干员
description: 按名字查干员的职业、稀有度与技能。用户提到具体干员、需要确认定位时激活；只是闲聊干员强度时不激活。
---

# 查干员

用 `search_operator` 查一位干员。参数只有一个 `name`，中文名或英文名都行。

返回值是一段文本，形如：

    能天使 · 狙击 · 6★ · 技能：过载模式

如果返回「没有找到」，先确认名字是否完整，再换英文名试一次。
```

frontmatter 三个字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `name` | 是 | 技能名，与目录名一致最省事 |
| `description` | 是 | **激活判据**，见下 |
| `source` | 否 | 来源标记，宿主会按实际来源标注 |

`description` 是全文最重要的一行：模型只看它来决定「要不要打开这个技能」。
写清两件事——**什么时候用**、**什么时候不用**。只写「查干员」不够，模型不
知道该在闲聊时激活还是查数据时激活。

正文是给激活之后的模型看的：参数、示例、常见错误、返回格式。写得像给同事
的交接说明，不要写「本技能旨在……」这种空话。

## 生效范围

- 技能索引在**新对话开始时**建立；装了插件、改了 SKILL.md，旧对话看不到，
  要新建一个对话；
- 停用插件，它的技能同时从索引里消失（同样只影响新对话）；
- 技能名与宿主自带的同名时，**宿主优先**，你的那份不生效——换个名字。

## 提示词里长什么样

宿主的系统提示词里有两处与插件有关：

1. **技能目录**：每条一行，宿主技能在前，插件技能在后并标注来自哪个插件：

   ```text
   - 数值计算［内置］：…
   - 查干员（我的插件）［用户］：按名字查干员…
   ```

2. **插件提供的能力**：只要存在插件提供的工具或技能，就多一节，把工具与
   技能按来源列出来：

   ```text
   ## 插件提供的能力

   工具 search_operator — 我的插件
   技能 查干员 — 我的插件
   ```

   宿主工具不出现在这一节里。

这两处都由宿主生成，插件不需要自己写。

## 什么时候该写技能

- 工具有一组**固定用法**（先查什么、再传什么），写在描述里太长；
- 工具的输出需要**解读约定**（字段含义、单位、缺省值）；
- 有几个工具要**按顺序配合**，模型自己猜容易错。

只有一两个简单工具、描述已经说清时，不写技能也行——多一个技能就多一份提示
词，也多一次模型判断。

## 几条禁忌

- 不要在 SKILL.md 里写死宿主的内部路径或实现细节；
- 不要教模型「绕过校验」「直接读文件」——能力边界是宿主定的；
- 不要把大段数据（表格、名录）塞进技能，那是工具该返回的东西；
- 不要依赖激活顺序：模型可能只激活其中一个。
