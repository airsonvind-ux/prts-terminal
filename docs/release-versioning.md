# PRTS Terminal 版本与发布策略

本文定义应用版本、数据版本与数据库结构版本之间的关系。目标只有两个：

1. 更新器能可靠判断“有没有新版本”；
2. 用户能知道这次更新大致属于“数据刷新”还是“内容大版本”。

## 1. 三层版本

| 名称 | 形式 | 作用 | 是否参与更新器排序 |
| --- | --- | --- | --- |
| 应用版本 | `X.Y.Z` | 标识一次公开发布 | 是 |
| 数据版本 | `YYYY.MM.DD` 或 `YYYY.MM.DD.N` | 标识 DB 数据快照 | 否 |
| 数据库结构版本 | 整数 `schemaVersion` | 标识 DB 结构兼容性 | 否 |

应用版本回答“这是第几次发布”。数据版本回答“这份数据是哪一天的”。结构版本回答“这份库能不能被当前代码读取”。

三者不能互相替代。尤其不能把游戏版本号直接塞进应用版本号，也不能用 build metadata（如 `0.1.0+20261022`）代替真正的版本递增，因为更新器不保证按它排序。

## 2. 应用版本的三个位置

### X：PRTS 代际升级

用于 PRTS 自身的重大升级、重大重构或不兼容变化，独立于游戏版本更新。

触发示例：

- 架构或数据模型发生不兼容变化；
- 产品形态发生代际变化；
- 正式进入新的稳定阶段。

X 变化时，Y 和 Z 归零。

### Y：游戏大版本

用于游戏大版本带来的数据变动，可以顺带包含较大的功能更新。

触发示例：

- 新主线/新活动体系/新肉鸽主题等大版本内容；
- 需要成批新增或重构数据表的更新；
- 跟随该游戏大版本一并交付的较大功能。

### Z：游戏小版本与小修复

用于游戏小版本带来的数据刷新，以及小范围 bug 修复。

触发示例：

- 新干员、新关卡、数值调整等常规数据更新；
- 小范围 UI、文案、交互修复；
- 不改变整体能力边界的小功能。

## 3. 发布规则

1. **一次发布至少递增一个位置。** 版本必须严格大于上一版。
2. **同时满足多个层级时，只递增最高的那一层，低位归零。**
   - 游戏大版本 + PRTS 代际升级：走 X；
   - 游戏大版本 + 普通功能：走 Y；
   - 游戏小版本 + 小功能/小修复：走 Z。
3. **只有 PRTS 自身重大升级、没有游戏大版本时，也可以走 X。** 此时 `dataVersion` 可以不变。
4. **多个游戏小更新合并到同一个发布周期时，只发一次、只递增一次 Z。** `dataVersion` 写最终快照，不为内部中间库烧版本号。
5. **DB 数据发生变化时，应用版本必须递增。** 即使代码没有变化，也不能只换 DB 不换版本；否则更新器不会向用户推送。
6. **DB 数据没有变化时，不无故更换 `dataVersion`。** 代码修复只递增应用版本，启动时不替换数据库。
7. **一次发布只对应一个数据快照。** 安装包内 DB、`meta` 表、`DATA_MANIFEST.json` 和 release notes 必须指向同一个 `dataVersion`。

## 4. 数据版本与结构版本

### dataVersion

- 格式：`YYYY.MM.DD`；同一天多次发布用 `YYYY.MM.DD.N`。
- 由维护者在生成 DB 时写入 `meta` 表。
- 用于 `db_seed` 判断运行时数据库是否需要替换。
- 不参与应用版本比较，不决定更新器行为。

### schemaVersion

- 从 `1` 开始递增。
- 只在数据库结构发生不兼容变化时递增。
- 应用启动时单独判断兼容性，不能拿 `dataVersion` 代替。

## 5. 发布示例

```text
0.1.0   首发
0.1.1   游戏小版本，数据刷新
0.1.2   小 bug 修复，数据未变
0.2.0   游戏大版本，数据成批更新
0.2.1   该大版本下的小版本更新
1.0.0   PRTS 自身代际升级
```

对应清单示例：

```json
{
  "appVersion": "0.2.0",
  "dataVersion": "2026.10.22",
  "schemaVersion": 1
}
```

## 6. 用户侧表现

- 用户只感知“应用更新”，不单独收到“数据更新”。
- 数据更新始终跟随一次应用版本发布。
- 用户关闭某个版本的更新提示后，同一版本不再重复弹出；新版本仍会提示。
- 数据更新在升级后的首次启动完成，不增加新的确认步骤。

## 7. 发布检查

每次发布前确认：

- [ ] 应用版本已按 X/Y/Z 规则递增，且大于上一版；
- [ ] `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 版本一致；
- [ ] `meta.dataVersion`、`DATA_MANIFEST.json`、release notes 一致；
- [ ] DB SHA-256 与发布记录一致；
- [ ] 发布 DB 已跑 data-contract；
- [ ] 只有代码修复、数据未变时，`dataVersion` 保持不变。

## 8. 暂不采用

- 不用 build metadata 作为版本排序依据；
- 0.1.0 不向用户单独推送数据包；数据随应用版本发布。发布构建可以使用单独的数据 Release 作为内部工件，但它不构成用户侧数据通道；
- 不把游戏版本号编码进应用版本号；
- 不为内部中间数据库单独发版。
